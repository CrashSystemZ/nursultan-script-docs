# Версии API

В каждом клиенте одна версия скриптового API. Скрипт говорит, какая ему нужна, первой строкой:

```kotlin
requireApi(1)
```

На клиенте старее указанного скрипт не загрузится и напишет понятную ошибку вместо непонятного поведения.
У новых методов написано, с какой версии они есть. Если про версию на странице ничего не сказано — значит, это было с самой первой.

## Чего `requireApi` не умеет

Он не спасает от **отсутствующего метода**. Твой скрипт — это исходник на Kotlin, который клиент компилирует при загрузке, а компиляция идёт раньше первой строки. Поэтому скрипт, который зовёт то, о чём старый клиент никогда не слышал, падает ещё до того, как до `requireApi` дойдёт очередь:

```
auto-jump.kts:14  Unresolved reference: arc
```

Именно это увидит твой пользователь. Смысл в `requireApi` всё равно есть, и его два: он ловит случаи, когда метод на месте, но работает не так, как в той версии, под которую ты писал, — и клиент упоминает запрошенную тобой версию в ошибке, когда ссылка не разрешилась.

Так что делай и то и другое: строку в начало файла, а версию — в описание скрипта, чтобы пользователь на старом клиенте понял, о чём ошибка:

```kotlin
name("AutoJump")
description("Прыгает за тебя. Нужен script API Nursultan 2 или новее")

requireApi(2)
```

## Во что обходится повышение версии

При обновлении SDK файл `.sdk/nursultan-script-api-vN.jar` заменяется новым, под новым именем, а `build.gradle.kts` переписывается на него. IDEA это замечает и один раз пересинхронизирует проект. Вот и вся цена — сами скрипты править не нужно.

## Что учесть

* Проси самую низкую версию, на которой скрипт правда работает. `requireApi(5)` в скрипте, который использует только возможности первой версии, без причины отрезает пользователей.
* Пакеты — исключение из всего этого: они следуют за версией Minecraft, а не за версией API. См. [Пакеты](../actions/packets.md).
