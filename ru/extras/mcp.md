# MCP для ИИ-агентов

**Эта страница написана для ИИ-агентов — Claude, Codex и всего остального, что умеет MCP.** Если ты человек,
тебе нужен только раздел «Как включить» ниже; остальное объясняет твоему агенту, что он сможет делать,
когда ты дашь ему ссылку.

Клиент умеет отдавать свой скриптовый рантайм как MCP-сервер. Подключённый агент пишет скрипт, заливает его,
включает и читает внутриигровую консоль — весь цикл, без того чтобы ты копировал файлы и перепечатывал ошибки.

## Как включить

В меню клиента открой вкладку **Скрипты** и нажми кнопку **MCP** в шапке, слева от кнопки консоли. Откроется
окошко — поставь галочку **Включён**. Уведомление скажет, поднялся сервер или нет, а при успехе ссылка уже
лежит в буфере обмена. Пока сервер работает, кнопка в шапке подсвечена.

Когда он поднят, в окне появляются ещё три кнопки:

* **Копировать** — кладёт ссылку в буфер заново.
* **Новый токен** — выпускает свежий. Старая ссылка перестаёт работать сразу же; пригодится, если ты
  засветил её там, где не стоило.
* **Новый порт** — берёт другой порт, если старый чем-то занят.

Последние две меняют ссылку — не забудь обновить её у агента.

Отдай эту ссылку агенту:

```bash
claude mcp add --transport http nursultan http://127.0.0.1:PORT/mcp/TOKEN
```

Ссылка постоянная — порт и токен сохраняются, так что сервер добавляется один раз и больше к этому
возвращаться не надо. Галочка тоже сохраняется: оставь её включённой, и при следующем запуске клиента сервер
поднимется сам, с той же ссылкой и не трогая твой буфер обмена. Снять галочку — остановить сервер и отменить
автоподъём.

Два момента. В ссылке лежит токен, так что **обращайся с ней как с паролем**: пока сервер включён, любой, у
кого она есть, может запускать скрипты в твоём клиенте. И сервер слушает только `127.0.0.1` — снаружи машины
до него не достучаться.

## Что получает агент

Одиннадцать инструментов. Всё ниже — то, что видит агент.

| Инструмент | Аргументы | Что возвращает                                                                        |
|---|---|---------------------------------------------------------------------------------------|
| `scripts_list` | — | все скрипты: `id`, `name`, `enabled`, `status` и `error`, если не скомпилировался     |
| `script_source` | `id` | текущий исходник скрипта                                                              |
| `script_deploy` | `name`, `source` | пишет `<name>.kts` в папку скриптов, скрипт сразу перекомпилируется                   |
| `script_delete` | `id` | выгружает скрипт и удаляет его файл                                                   |
| `script_enable` | `id` | включает скрипт, ровно как нажатие его бинда                                          |
| `script_disable` | `id` | выключает                                                                             |
| `script_settings` | `id` | `status` загрузки, бинд и все настройки с их типом, значением, границами и вариантами |
| `script_setting_set` | `id`, `key`, `value` | пишет одну настройку; для настройки-кнопки — нажимает её                              |
| `script_bind_set` | `id`, `key`, `mods` | перевешивает бинд, `UNKNOWN` — снять                                                  |
| `console_tail` | `sinceId`, `limit` | строки консоли, свежие в конце, плюс `lastId` для следующего вызова                   |
| `game_state` | — | `inGame`, `singleplayer`, измерение, позиция игрока                                   |

### Настройки

`script_settings` отдаёт у каждой настройки поле `kind`, а `script_setting_set` ждёт значение под этот тип:

| kind | что слать |
|---|---|
| `checkbox` | `true` / `false` |
| `slider` | число в пределах `min`..`max` |
| `rangeSlider` | `{"min": 1, "max": 4}` |
| `input` | строку |
| `colorPicker` | целое ARGB |
| `selectable` | `name` одного варианта |
| `combo` | массив имён вариантов — всё, чего в нём нет, снимается |
| `hotkey` | `"G"` или `{"key": "G", "mods": 2}` |
| `button` | что угодно; отправка нажимает кнопку |

Три формы, которые не являются простым скаляром — `rangeSlider`, `combo` и объектная запись `hotkey`, —
принимаются и настоящим JSON, и строкой с JSON внутри: как отдаст твой клиент, так и сойдёт.

Настройка, вложенная в чекбокс, приходит с ключом через точку и полем `parent`, и писать её надо тем же
ключом через точку:

```json
{"key": "Fancy",       "kind": "checkbox", "value": true}
{"key": "Fancy.Alpha", "kind": "slider",   "value": 0.5, "parent": "Fancy"}
```

Сначала читай, потом пиши: настройка может быть невидимой (`visible: false`), потому что её выключила другая,
а у вариантов есть собственное `name`, которое надо передавать дословно.

## Цикл

```
script_deploy  ->  scripts_list  ->  script_enable  ->  console_tail  ->  правка  ->  script_deploy
```

`script_deploy` только пишет файл. Компиляция идёт сразу после, сама по себе, — поэтому следующим вызовом
смотри `scripts_list` и поле `status`. `ERROR` значит, что не собралось, а текст лежит в `error`; включить
скрипт не выйдет, пока это не починено.

`console_tail` инкрементальный. Первый вызов отдаёт буфер и `lastId`; передай его обратно как `sinceId` — и
получишь только новое. Это самый дешёвый способ следить за скриптом, не перечитывая всё заново.

Нумерация строк начинается заново, когда человек перезапускает игру. Обрабатывать это тебе не надо: курсор впереди самой свежей строки считается началом с чистого
листа, и в ответе приходит `"reset": true` — чтобы ты понял, что нумерация пошла сначала, а не консоль
замолчала.

## Чего ты не можешь

**Ты не можешь играть.** Бегать, кликнуть ПКМ по торговцу, открыть сундук — нет. Когда тест этого
требует, либо проси человека, либо пусть скрипт сам готовит мир: серверные команды ему доступны.

```kotlin
chat.sendToServer("/summon wandering_trader ~ ~ ~3")
chat.sendToServer("/setblock ~ ~ ~2 minecraft:suspicious_gravel{item:{id:\"minecraft:emerald\",count:1}}")
```

**Перед этим посмотри `game_state`.** Такие команды работают только в одиночке с включёнными читами; на живом
сервере их в лучшем случае отклонят, а в худшем, человеку прилетит за читерство. Если `singleplayer` false —
проси, а не отправляй.

**Скомпилировалось — не значит работает.** Скрипт может собраться и умереть в момент срабатывания обработчика:
нерезолвнутый символ внутри `on<...>` линкуется только при первом вызове этого обработчика. Так что никогда не
считай скрипт проверенным по `status: READY` — включи его и прочитай консоль.

**`onEnable` выполняется до подписки обработчиков.** Пакет, отправленный прямо из `onEnable`, собственный
`on<PacketSendEvent>` этого же скрипта не увидит. Отправляй из тикового обработчика.

## Как писать сам скрипт

Про язык и API — вся остальная документация, начни с [Первого скрипта](../start/first-script.md). Учти, что
[песочница](limits.md) запрещает рефлексию, файлы и сеть: скрипт, который к ним тянется, не загрузится, а не
поведёт себя странно.

Первой строкой указывай нужную версию API, подробности — в [Версиях API](api-versions.md):

```kotlin
requireApi(1)
```
